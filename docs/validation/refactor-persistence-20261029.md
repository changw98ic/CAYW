# 持久化测量与投影缓存优化

本记录对应 2026-10-29 重构方案的阶段 5。冻结起点为 `e738dae1af73bf0ad3fe15f729a4557a2d9f4d24`。本轮使用真实 SQLite 文件和公开 `SessionStore` API。没有运行模型，也没有执行工具体。

## 环境与复跑入口

机器为 Apple M4、16 GiB、macOS 27.0.1（26A434）、arm64。工具链为 Rust/Cargo 1.95.0。数据库使用仓库锁定的 rusqlite，实际 SQLite 版本为 3.53.2。正式测量的数据库放在 `/Volumes/ORICO` 外置固态卷，文件系统为 APFS。前后均为 release 构建，所有测量串行执行。

在仓库根目录执行下面一条命令，可复跑一个长历史普通写入场景。默认在新的临时目录创建数据库，JSON 输出包含原始样本、每次调用前的事件游标、消息数和前一操作：

```sh
cargo +1.95.0 run -p cayw-core --release --locked --example refactor_persistence_bench -- --size long --category normal --sessions 1
```

三档输入为每会话 64、512、4,096 个工作量单元。`--category` 可选 `message_update`、`normal`、`mixed`，`--sessions` 可选 1、2、8、32。多会话在同一个存储连接上依次轮流追加。它没有同时发起写入，不能用于判断并发竞争或事务锁等待。

若需要保留 JSON，可追加 `--out <新文件路径>`；`--db <新数据库路径>` 指定新的数据库文件。macOS 的 `/usr/bin/time -l` 可在预先编译的二进制外记录进程峰值常驻内存。不要用包含 Cargo 构建的峰值代替二进制进程的峰值。

## 输入与计时口径

- `message_update`：流式消息更新及其合法生命周期。
- `normal`：每个单元完成一轮用户消息、助手消息和轮次终态，再追加 Host 事件。历史消息持续增长。
- `mixed`：流式更新与 Host 事件交替，并记录代表性的工具开始、执行标记、工具终态及配对结果。这里只写 Core 记录，不运行 Host 执行器，不包含完整 Runtime 的来源绑定与执行登记。

工作量单元不等于追加次数。结果分别记录计划追加次数、实际事件行数和每类操作样本数。每次测量结束后核对会话为 Idle、游标与计划一致、消息数一致、事件行数一致和会话行数一致。任何不一致均中止该场景。

每个样本计时从公开存储方法调用前开始，到调用返回结束，包含数据库提交。输入事件在计时前生成。`timed_appends_per_second` 只使用追加操作的样本；创建会话、开始/结束 attempt、最终读取另计。它不等于整个进程从启动到退出的吞吐。

进程峰值常驻内存包含输入准备、结果样本和存储处理，不能解释成投影缓存本身的内存。数据库 checkpoint 在存储连接关闭后执行，只记录关库后的文件状态，不测活跃 checkpoint 成本。

## 第一项优化：普通写入复用

普通 `mutate` 使用已有的投影缓存读取入口。只有数据库中的完整 JSON 与缓存相等时才复用已解码的会话；命中后仍执行 wait 日志校验。修改前取出缓存，使用 `Arc::make_mut` 取得可修改会话。持久化后，在同一事务读取刚写入的投影字符串，提交成功后回填缓存。错误路径保持缓存为空，下次读取从已提交数据重建。

第一项优化只改普通写入的缓存复用，测量时仍是一个槽位。完整投影编码、完整 JSON 读取与比较仍有成本。没有改 Core v3、索引、WAL、FULL 或 wait 日志校验。没有以游标相等替代 JSON 一致性检查。后面的按会话缓存属于独立的第二项优化。

Core 定向测试已经覆盖独立连接写入、恢复、投影损坏和 wait 记录损坏。新增的普通写入 COMMIT 失败测试使用同连接的延迟外键约束，确认失败后历史不变，去除故障后同一次操作只提交一条事件。最终检查结果见实施记录。

## 第二项优化：有界的按会话缓存

诊断后将缓存改为按会话保留。上限为 32 个条目和合计 16 MiB 的投影 JSON。两项上限同时执行，淘汰最久未使用的条目。单条 JSON 超过 16 MiB 时仍正常读取、验证和写入，只跳过缓存。该预算限制保留的 JSON 字节；解码对象与分配器开销另占内存，不能把它写成进程或缓存总内存的硬上限。

每次读取仍从 SQLite 取完整投影并比较完整字符串。只有相等时复用解码对象，而且仍校验 wait 日志。普通写入和流式更新只移除自己正在修改的会话，提交成功后发布新条目。失败时该会话下次从已提交数据重建，移除操作不清空整个缓存。若写入开始时未命中且缓存已满，最初加载仍可能按容量淘汰另一个会话；之后写入失败不会撤回这次缓存淘汰，后果只是下次重新解码。没有给 fork、恢复等其他写入路径增加失效通知；完整 JSON 比较会识别它们的持久变化。

新增回归核对 32 会话轮转复用、最久未使用淘汰、JSON 字节预算、超大条目跳过、提交失败保留其他会话，以及轮转后独立连接的写入、恢复和同游标损坏。原有 wait 日志损坏、流式历史和旧 v3 样本测试继续执行。

据此保留按会话缓存：这组多会话输入中的真实未命中消失，普通和流式写入的代表操作耗时下降，release 对照给出了收益和额外内存成本。缓存条目数或字节超过上限时仍会淘汰；不承诺任意活跃会话集合均命中。单会话长普通吞吐的本次变化为 -3.5%，p50 基本不变，不能宣称第二项优化在所有配置提速。没有进一步改变存储格式、FULL、索引或一致性检查。

## 查询与测量限制

两条生产查询的 `EXPLAIN QUERY PLAN` 均使用实际索引。按类型取事件和 wait 日志在本机均选择 `core_events_by_type`。没有出现对 `core_events` 的无索引全表扫描。wait 日志选择有效索引即可，不要求强制选择某个部分索引。

产品公开 API 不提供缓存命中次数或分段计时，仓库基准保留端到端调用时间。以上命中与分段结果来自独立插桩副本，不用插桩耗时替代正式 release 性能结果。诊断没有覆盖 fork、recover、审批查询和列表读取；这些路径的正确性由各自测试验证。FULL 表示保留原来的持久化要求，不代表每次提交恰好执行一次文件同步。

本轮没有定义用户负载的性能目标，因此不作“吞吐够用”的判断。其他 macOS 架构、真实模型任务与并发写入负载不在这份结果的已验证范围内。
