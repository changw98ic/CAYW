## 默认 CLI 的实际等待值

服务端和客户端原来分别固定 360 秒。配置 Task 900 秒时，`task.resume` 仍会先被传输层截断。现在 `cayw serve` 根据正式任务期限加 60 秒计算 IPC 请求等待上限，同一变量同时用于 `ServerConfig` 和 `runtime.health.request_timeout_ms`。默认 Task 300 秒仍对应 IPC 360 秒，配置 900 秒对应 960 秒。

客户端通过认证短连接读取实际值，关闭该连接后，再为执行和观察连接采用该值。缺失、非法类型、零值或不可表示的期限在任务入队前报错。没有新增超时选项或配置字段，没有保留旧服务端回退契约。通用 Runtime SDK 不推测 IPC 设置；自行编写的 IPC 宿主应报告自己的实际传输配置。

`cli-long-380s-01` 实际使用两个 CLI 程序，不通过 SDK 另建长等待服务。配置 Task 900 秒，Host 等待与单次调用 240 秒；客户端没有超时参数。固定 HTTP 流保留原始响应和发送时间，实际请求持续 380.007 秒，CLI 执行 380.156 秒。Task completed、Session idle，重开新进程后消息、事件、任务和审计记录一致，没有第二个 HTTP 请求。

固定响应完整报告 160 token、预留 0、用量已知；它不计真实模型预算。`cli-long-audit-01/verification.json` 的 41 项独立检查通过，核对程序、源码归档、全部 CLI 原输出、完整响应、账本与重开结果。该场景不证明任意排队时长，也不改变业务期限或断连清理。

客户端新增实际 IPC Ctrl+C 回归，与 SDK 共用同一行为检查。原 Task、Worker、Attempt、fence 一致，顺序为取消请求、取消确认、原 Task 终态，HTTP 请求一次。该取消场景与 380 秒完成场景分别记录。

## 预算锁与 Cells 说明

`budget_locks` 从保存 `Arc<Mutex<()>>` 改为 `Weak<Mutex<()>>`。获取锁时，在表的同一互斥区清死键并升级现有弱引用；仍有持有者或等待者时复用原锁。没有在单次请求结束时直接移除条目，因此新请求不会绕过旧等待者拿到第二把锁。空闲期间可能保留上次集合的死键，下一次获取任意根锁时清理；没有声称表会在空闲时主动清空。

三个回归实际验证大量根释放后的清理、已进入 Pending 的排队者与持有者共锁、取消等待者后锁对象释放及后续串行。`futures::poll!` 明确证明等待已经发生，不靠固定毫秒断言。模型请求的预留、未知状态、持久终态和费用逻辑未改。

Cells 工具说明明确 `store(key,value,expected_version)` 三参数必填，创建用 0，更新用 `load` 返回的版本。`load` 返回 `{version,value}` 或 null。说明同时要求 `vm_alive=true` 或 `has_more=true` 时使用原 `cell_id` 和 `next_cursor` 等待，不能重放 exec。没有把版本参数改为可选，也没有放宽 Runtime 完成检查。

`cross_exec_store_load_conflict_and_reopened_readback` 经真实 SQLite、正式授权装饰器和 Cells 执行路径验证创建、版本冲突、正确更新、关闭重开和读取。它与完整工作区测试均通过。
