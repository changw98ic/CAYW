# 记忆、上下文与主动工作设计

[项目说明](../README.md) · [架构文档](architecture.md) · [开发路线图](development-map.md)

本文是目标设计，不表示已经实现。当前行为以源码、[架构文档](architecture.md)和各包说明为准；交付拆分与状态见[路线图](development-map.md)。

本文来自 2026-11-09 提出的《记忆、上下文与主动工作统一方案》，已对照代码审查修订，并纳入同日确定的决定：

- 主 session 是一个默认工作区，目录为 `~/CodeAsYouWish`。
- 模型方案每台设备保存一份，所有工作区共用，各自选用。
- 本地 Client 使用模型 auto 审批。模型通过 CodeMode 查询和决定待审批操作，不要求用户人工审批。
- Git 恢复点默认开启；没有 Git 时发出警告，继续工作。
- 不设用量上限。用量只记录并显示，累计用量不拒绝请求。
- 用户说忘掉后，以后不再使用那段内容。日志留在磁盘上，不擦除。

本文用到的几个词：

- brief：一个 session 当前工作状态的有界视图。
- Dream：整理摘要引用结构的后台任务。
- 前沿：某条派生流水线连续处理完成的位置。

## 与原方案相比的修改

| 原方案（章节） | 本设计 | 原因 |
| --- | --- | --- |
| 模型在 auto 模式下自行审批（一、十二） | 保留。模型通过 CodeMode 决定待审批的原操作，记录模型审批来源。 | 按用户要求实现，不增加人工审批。 |
| `~/CodeAsYouWish` 是用户级目录，保存日志、模型配置、预算和通知（一） | 主 session 是默认工作区，目录是 `~/CodeAsYouWish`；它的数据库与其他工作区一样位于 `<CAYW_HOME>/workspaces/<目录摘要>/`。 | 复用工作区结构和 Client 路由，不出现第二个数据根。 |
| 模型配置放在用户级目录（一） | 设备模型列表 `<CAYW_HOME>/models.json`；工作区只保存自己的方案选用。 | 配置过的模型在所有工作区都能用，只有一份权威配置。 |
| 预算分为用户级账户、工作区账户和用户总账（一） | 每个 session 的预算树只记账，不设用量上限；工作区合计和设备合计只是汇总视图。 | 现有账本只有按会话血缘划分的预算树。用量只记录，不作为拒绝请求的上限。 |
| `log_id` = session 前缀 + 递增序号，可以留空洞（二、四） | `log_id` 就是现有的 `(session_id, cursor)`；游标保持连续。 | 现有读取逐条检查游标连续；避免两套身份。 |
| 大正文写入 ContentStore 或日志层内容对象（三、四） | 只写入 ContentStore，经 `result.*` 读取；不另设 `read_content`。 | 已有统一结果入口；不建第二套内容存储。 |
| `required_budget` 按同一分页协议继续读（三） | 游标不变；调用方把 `max_output_tokens` 提高到不少于 `required_budget` 后再读。 | 用原预算重读会得到同一空页。 |
| `max_output_tokens` 的单位待定（三） | 已确定为序列化 UTF-8 字节预算；32 KiB 是 `auto_externalize_threshold_bytes` 的默认值。 | 与现有契约一致。 |
| 主 session 能否操作工作区文件前后不一（一、三） | 主 session 只操作自己的工作区；其他工作区的读写都派给执行 session。 | 统一边界。 |
| 上下文窗口 W 没有来源（七） | 模型方案增加 `context_window`；C 按将要发送的输入计算，并用 Provider 报告校准。 | 现有模型配置只有输出上限。 |
| WorkItem 以验收结果完成，但没有验收记录（十一） | 增加验收记录；只有程序核对的结果或用户确认才能写入“通过”。 | 模型自报不能代替验收。 |
| 没有仓库时在工作区初始化 Git（十二） | 使用 CAYW 私有的快照仓库，不在用户目录创建 `.git`，不碰用户仓库。 | 不改变用户目录和仓库；不受用户仓库形态限制。 |
| 同一 session 不并发两个有写权限的 Attempt（十三） | 每个 Session 同时只有一个活动 Task；并行工作使用独立 Session。 | 与现有队列一致。 |
| 维护请求不占整树锁、不预留全部余额，且单次和总维护额度有界（十五） | 新增“维护请求”类别：只记这次调用的用量上界，不设上限；在途记录和未知用量不阻塞前台。 | 现有账本每次预留整棵预算树的余额，任何未结预留都会拒绝后续请求。维护请求如果走这条路径，会挡住用户的下一条消息。 |
| 统一读取层处理删除，覆盖查询、界面和导出；先写墓碑，再物理清除（十六） | 用户说忘掉后，以后的回答、摘要、压缩和记忆不再使用那段内容。日志留在磁盘上。按游标读取仍返回原事件。不写墓碑，不物理清除，不追查副本。 | 忘掉只影响以后怎么用，不改已经写下的日志。 |
| 统计“可确认费用”（十九） | 统计 token、未知用量和费用未知的请求数。 | 现有模型方案没有价格字段，费用始终未知。 |

## 整体结构

CAYW 以一个长期存在的主 session 作为用户入口。WorkItem 表示一项持续的工作。执行 session 承担具体工作。所有 session 共用同一套日志、摘要、查询、预算和维护能力。

- 主 session：负责对话、记忆、工作路由、询问和结果交付。
- 执行 session：负责推理、CodeMode 执行和产物验证。
- WorkItem：把多次执行、等待、监控和交付连成一项工作。它是持久记录，不是另一份模型上下文。

| 部分 | 保存什么 | 上下文方式 |
| --- | --- | --- |
| 主 session | 用户对话、基础记忆、偏好、工作目录、询问与通知记录 | 常驻记忆加滚动历史；淘汰后可以查回 |
| WorkItem | 目标、验收条件与结果、状态、执行关联、等待条件 | 持久记录 |
| 执行 session | 工作过程、工具调用和结果、阶段进展、产物 | 持续摘要加后台压缩 |
| 共享底座 | 原始日志、稳定引用、派生版本、brief、Dream、维护调度 | 按来源区间增量处理 |

### 三种关系

1. 业务归属：WorkItem 属于主 session，用于路由、展示和查询。
2. 执行父子：执行 session 是独立的执行根，不挂到主 session 的执行树下。它需要并行分工时，再建立自己的子 session（现有 `agent.run`）。
3. 预算归属：每个 session 的模型用量记在它自己的预算树上（见“预算账户”）。维护请求记在被维护 session 的预算树上。

三种关系分开记录。一个工作区的任务不会因为属于主 session，就和其他工作区的任务共用预算锁或排队等待。

### 主 session 工作区

- 主 session 是一个默认工作区，目录是 `~/CodeAsYouWish`，按当前用户的 `HOME` 解析。目录不存在时，Client 启动时创建它（权限 0700），并登记为工作区。
- 设备配置可以覆盖这个目录，便于测试和多账号。测试和验收脚本设置 `CAYW_HOME` 时，必须同时覆盖主 session 目录，避免读写真实用户的记忆。
- 主 session 工作区和其他工作区结构相同：状态在 `<CAYW_HOME>/workspaces/<目录摘要>/`，包括 SQLite、Session 和插件启用关系。
- 主 session 工作区里只有一个长期的主 session。它的 `session_id` 不因压缩、淘汰、重启或模型切换改变。
- 目录中保存用户可以直接查看的内容：基础记忆与偏好（`memory/`，见“基础记忆与偏好”），以及主 session 交给用户的文件。
- 已有目录读取失败或损坏时，在原位置报告，不重新初始化覆盖。
- Client 启动时总是打开主 session 工作区。
- 主 session 只操作自己的工作区。需要检查、编辑、构建或运行其他工作区的内容时，派给那个工作区的执行 session。
- 主 session 缓存其 WorkItem 关联工作区的 brief 和引用。未关联工作区只经 Client 查询工作区摘要，不读取其 session 内容。Task、Session 和产物的实际状态以所在工作区的 Runtime 为准，经事件和到期对账更新。

### 设备模型列表

- 模型方案每台设备一份，保存在 `<CAYW_HOME>/models.json`（私有文件，权限 0600）。
- 所有工作区（包括主 session 工作区）都可以使用列表中的任一模型。设备模型列表保存一个默认方案，由 `cayw conf` 维护；新工作区默认使用这个方案，已有工作区保留原选用，也可以选用列表中的另一个。新工作区不需要单独配置模型。
- `cayw conf` 仍是唯一的交互式首次配置入口，写入设备模型列表。
- 密钥规则不变：可选明文 `api_key`；编辑时同一 `service`、`api`、`base_url` 和 `api_version` 下留空表示保留原值；删除必须显式清除；服务、API、地址或版本任一改变时，必须提供新密钥或显式清除；公开输出不回显密钥。
- 每个模型方案增加 `context_window`（模型上下文窗口，单位 token）和可选的 tokenizer 标识。`cayw conf` 询问窗口，常见模型给出默认值。
- 没有任何模型时，Client、TUI 和 WebUI 照常启动；第一次执行 `prompt`、`enqueue` 或 `resume` 才返回 `model_not_configured`。
- 不维护旧版本迁移：只读取设备模型列表和工作区 `model-selection.json`，不导入每工作区旧列表或旧 `config.json.model`。完全显式 Headless 的 `--config` 保留它自身的模型配置语义。
- 完全显式 Headless 仍只使用 `--config` 中的 `model`，不读取设备模型列表。

## 预算账户

- 预算树（现有）：一个 session 和它派生的子 session 的用量记在同一棵树上，以 `budget_session_id` 为根。它是记账单位。
- 不设用量上限。token、未知用量和费用状态只记录并汇总显示，累计用量不会拒绝请求。现有的 `max_total_tokens` 是待移除的阻断上限。
- 付费模型会一直产生费用，直到用户自己停止。程序不因此增加确认，也不拒绝请求。
- 在途预留和结果不明的用量仍要记录和核对，避免把没确认的用量当成零，或把同一次用量算两次。这是记账，不是限额。
- 主 session 的模型用量记在主 session 的预算树上。每个执行 session 是独立的根，用量记在自己的预算树上，不并入主 session。
- 工作区合计和设备合计是汇总视图：Client 汇总各工作区的账本。它们不形成第二套账本。
- 主动规则记录自己派工的用量，只统计，不设上限。

## 身份和处理单位

| 标识 | 含义 | 来源 |
| --- | --- | --- |
| `session_id` | 主 session 或执行 session 的身份，始终不变 | 现有 Core |
| `work_id` | 一项 WorkItem 的身份 | 新增 |
| `task_id` | Runtime 中一次执行任务的身份 | 现有 Queue |
| `log_id` | 一条原始事件的身份，即 `(session_id, cursor)`，文本写作 `<session_id>:<cursor>` | 现有 Core 游标 |
| `user_turn_id` | 一次用户请求的处理轮次，等于为该请求创建的 Task 的 `task_id` | 复用 Task |
| `model_cycle_id` | 一次模型响应及其工具结果，对应 Runtime 的一个模型轮次（turn） | 复用 turn |
| `tool_group_id` | 同一次模型响应（一条 assistant 消息）发出的工具调用组 | 按所在 assistant 消息确定 |
| `summary_id` + 版本 | 一份摘要 | 新增 |
| `compression_id` + 版本 | 一份压缩结果 | 新增 |
| `context_epoch` | 当前采用的上下文版本 | 新增 |

**用户轮次**从用户请求被接纳开始，到该请求的最终答复、明确失败或取消结束。一个轮次可以包含多个模型轮次和多组工具调用。

- 主 session 的轮次在它回答，或确认并派发工作后结束，不等被派发的工作完成。后续进展、用户补充和交付分别形成新的事件。
- 等待执行、跨天和上下文替换不会结束轮次。执行中断而没有结束结果时，记为中断。
- 明确的新请求建立新轮次。属于当前请求的补充和纠正关联到当前轮次和工作，不另调用模型判断边界。当前轮次已经结束时，纠正建立新轮次，并关联原 WorkItem。
- 主 session 正在处理上一条消息时，新消息先保存为输入（`received`），当前 Task 结束后进入下一个 Task；属于当前请求的补充在下一个模型请求边界注入。
- 程序发起的 Task（例如交付工作结果）记录来源，不算用户轮次。

**模型轮次**是一次模型响应，加上它发起的工具调用和结果处理。摘要分段可以在已完成的模型轮次边界切分，不必等用户轮次结束。

**工具组**是同一次模型响应发出的工具调用。CodeMode cell 内部的子调用各有记录，并关联到外层 cell。日志分别记录调用和结果。装配输入时保留协议要求的配对，不能把未完成的工具交换当作已完成的历史丢掉。

**摘要段**是后台摘要器处理的一个固定来源范围。它可以是完整轮次、长轮次中的一段、一个阶段，或大工具结果中可以独立阅读的部分。摘要段只是处理单位，不改变轮次和工具状态。活动 cell 已产生的历史输出页可以摘要；cell 的身份、游标和状态单独保留。

## 统一 CodeMode 执行

主 session 和执行 session 的模型都只通过 `execute_code` 执行操作。主 session 用它读取日志、检索摘要、管理 WorkItem、派工和读取 brief；执行 session 用它读写工作区、运行测试和查询外部服务。不另设通用命令入口。

模型编写有界脚本，在 cell 内组合工具、筛选结果和处理分页，只把下一步需要的信息返回模型。Host 的事务提交、预算计算、上下文装配、事件投递和调度是程序内部逻辑，不调用模型。

### cell 状态

活动 cell 的状态单独维护。现有记录保留 `cell_id`、所属 session 与 Task、真实状态、已返回的输出页、下一页游标、已完成的子调用和仍需核对的 `outcome_unknown`。模型轮次和工具组由 `parent_call_id` 关联；当前等待点由 cell 状态和游标表示。需要新增的关联字段在 Runtime 层定义。上下文替换后，模型继续使用原 `cell_id` 和游标，用 `wait` 读取后续输出，不重新执行原脚本。

### 工具结果减量

处理顺序固定：

1. 工具源头按范围、字段、分页或过滤条件返回。
2. CodeMode 脚本内做确定性筛选、聚合和提取。
3. Host 有界呈现结果，附完整结果引用和截断信息。
4. 后台摘要器处理已固定的历史内容。
5. 执行 session 的压缩器整理累计历史。

前三步减少当次输入，后两步管理长期上下文，彼此不能替代。

工具返回保留调用身份、真实状态、退出码、错误摘要、截断标记、原始规模、返回规模和回查入口。测试输出优先保留失败案例与汇总；JSON 按字段或查询表达式提取；长文本支持有界搜索和分段读取。

### 大正文与单位

- 大正文只写入 Device 的 ContentStore，经 `result.store/get/batch_get/search/release` 读取。模型收到引用和必要摘录。只有写入成功才返回引用。
- 引用增加来源 `log_id`。长期证据使用 `log_id`；结果引用用于读取正文。
- 自动外置门槛是 `auto_externalize_threshold_bytes`，默认 32 KiB，可以配置，0 表示关闭。`result.get` 的单页上限另为 32 KiB。字节门槛与 token 预算分开计量。
- `max_output_tokens` 是现有字段名，单位是序列化 UTF-8 字节，不是模型 token。
- 一页放不下下一项时，返回 `required_budget`，本页为空，游标不变。调用方必须把 `max_output_tokens` 提高到不少于 `required_budget`，再用同一游标读取。所需预算超过上限时，返回明确结果（外置引用或失败），不能静默跳过。

## 日志和读取层

### 身份

- 每条原始事件的身份就是 Core 现有的 `(session_id, cursor)`。游标在 session 内连续递增，跨天不重置；迁移不改变已有游标。日志不删除。
- 文本形式写作 `log_id = <session_id>:<cursor>`。
- 消息、工具调用开始、工具结果、控制操作、任务状态、派工和通知分别追加为事件。
- 原始内容不可变。小正文保存在事件中；大正文保存在 ContentStore，事件只保存引用。摘要中不复制整份原文。
- 存储继续使用 SQLite 的事件和事务。读取只依赖逻辑身份，不依赖表行位置或文件偏移。以后如果增加按天切分的文件后端，也必须保持连续游标和同一读取协议；按天切分文件时，切换只发生在完整记录的边界。

### Fork

- Fork 产生新的 `session_id`。新 session 的第 1、2 条事件是 `SessionCreated` 和 `SessionForked`，后者保存复制的历史和来源游标。
- 新 session 引用来源 session 在来源游标之前的摘要和压缩，不重新生成，也不复制。只采用完全落在这个范围内的摘要；其余部分按原文处理。
- 新 session 从第 3 条事件起独立生成派生视图。

### 前沿

| 字段 | 含义 |
| --- | --- |
| `latest_cursor` | 已完整记录的最新事件，即现有 Session 游标 |
| `covered_cursor` | 某条派生流水线连续处理完成的位置 |

摘要、压缩、记忆写入和 Dream 各自维护 `covered_cursor`。后面的任务先完成，不能让前沿跳过前面尚未处理的内容。

### 读取接口

| 接口 | 作用 |
| --- | --- |
| `read_log(log_id)` | 读取一条原始事件 |
| `read_logs(ids, budget)` | 按预算批量读取 |
| `read_events(session_id, range, filter, budget)` | 读取一段事件，可以按类型、工作和时间筛选 |
| `search_summaries(query, filters, budget)` | 检索轮次、阶段和分段摘要 |
| `get_session_brief(session_id)` | 读取当前状态视图 |

大正文继续用 `result.get` / `result.search` 读取。

这些接口作为 CodeMode 能力提供，和其他能力一样经过 Host 校验、调用记录和预算。读取范围限定如下：

- 执行 session 只读取自己的日志和派生视图，以及派工时传入的 WorkItem 信息。
- 主 session 读取自己的日志，以及其 WorkItem 关联的 session。跨工作区读取经唯一 Client 路由到所在工作区的 Runtime。
- 不能按任意 `session_id` 读取未关联的 session。
- 这些接口按游标返回原文，不因忘掉而隐藏或改写。预取、装配、新的摘要、压缩和记忆跳过已忘掉的范围（见“忘掉”）。

索引按 session、游标范围、时间、工作关联和内容类型增量更新。检索先用索引和关键词，不依赖向量库。

### 固定来源范围

物理封口表示一个文件或段不再追加；逻辑封口表示某个处理范围的来源已经固定。后台摘要和 Dream 只需要逻辑封口。普通工具输出完整写入后即可读取。

### 提交顺序

以下事实先持久提交，再生效或发起动作：

- 用户请求的接纳；取消、暂停、恢复和工作状态的改变。
- 放行规则的修改、用户对询问的回答，以及相关作用域的版本。
- 派工意图，以及 `dispatch_key` 与 `task_id` 的绑定。
- 外部动作的开始意图和结果。
- 通知的发送意图和回执。
- 用户对记忆的直接修改，以及要求忘掉的记录。

摘要、索引和 brief 等可以重建的数据按批提交，不逐条同步磁盘。

## 持续摘要链

### 触发

- 每个完成的用户轮次都生成轮次摘要，包括普通问答和闲聊。短确认类轮次直接复用原文，不调用模型。
- 长轮次不必等结束。未摘要内容达到分段启动量（约 4K token），或出现子任务完成、阶段切换等事件时，在最近的完整模型轮次或工具组边界固定范围，提交后台分段摘要。
- 轮次结束后，用已有的分段摘要加最后的新增内容生成轮次摘要，不重新读取整轮原文。

### 结构

`summary_id, version, session_id, kind, source_ranges, child_summary_refs, text, evidence, keywords, stage_hint`

- `kind`：`segment`、`user_turn` 或 `stage`。
- `source_ranges`：固定的原文游标范围。
- `child_summary_refs`：固定到具体的摘要版本。
- `text`：目标、进展、结果、决策、约束变化和未完成事项。
- `evidence`：必要的出处（`log_id`）。生成时不设固定条数上限，优先保证召回；读取时按调用方预算展开。
- `keywords`：少量检索词，闲聊也生成。
- `stage_hint`：摘要器顺带返回的阶段提示，不单独调用模型判断阶段。

摘要保存在上下文模块自己的表中，不写入 Core 事件，因此不受单条事件的体积上限约束。

### 阶段

阶段边界按以下顺序确定：

1. 明确的 Runtime 事件，例如子任务完成、失败、取消或切换阶段。
2. 内容达到分段规模。
3. 摘要器返回的 `continue`、`goal_completed`、`topic_changed` 或 `approach_changed`。

同一目标因内容过长分成多个阶段时，用 `continuation_of` 关联。阶段只有 `open` 和 `ready` 两种状态。`goal_completed` 只是语义提示；WorkItem 是否完成由验收记录决定。

### 大工具结果

大结果可以独立分段，每段指向同一个工具调用。结构化结果按对象、数组项、记录或完整文本块拆分，不在 JSON 字符串和协议消息中间截断。摘要只描述已固定的部分；活动 cell 的当前游标、运行状态和未确认的动作留在当前状态区。

### 发布

- 每个摘要任务固定来源范围和输入版本。生成期间新增的内容进入后续任务。
- 结果按来源区间登记。旧任务晚完成，不覆盖新状态。
- 前沿只在前面所有必要范围完成后推进。
- 摘要生成不进入前台等待路径。失败时该范围保留原文，后台按退避重试，并记录失败次数。
- 发布前跳过已经忘掉的来源（见“忘掉”）。

## 约束账本与工作 brief

### 约束账本

每个 session 保存用户原始要求的引用、明确的控制操作，以及 Runtime 任务状态。先写原始记录，再更新账本引用。

账本不做另一轮自然语言理解。模型读取原话和上下文，形成行动计划；程序记录原话来源、当前工作版本和执行状态。没有解释清楚的要求保留原文入口。

WorkItem 保存目标、范围、验收条件与结果，以及询问记录的引用；session 账本保存用户说过什么和控制事件。两者通过 ID 关联，不重复保存整段内容。

摘要、Dream 和 brief 可以反映用户要求和运行事实，但不能派工、取消工作或改变验收状态。

### brief

`get_session_brief(session_id)` 返回有体积上限的当前视图：

`brief_version, covered_cursor, latest_cursor, current_goal, runtime_status, progress, pending, artifacts, related_summary_refs`

- 即时状态来自 Runtime；语义进展来自已完成的摘要。
- `covered_cursor` 是摘要流水线的前沿。调用方比较它和 `latest_cursor`，判断是否需要补读增量事件。
- brief 不累计完整历史，也不代替压缩结果。主 session 用 brief 了解工作；执行 session 用自己的上下文继续工作。

## 上下文预算与版本

### 预算口径

- W：模型上下文窗口，来自所用模型方案的 `context_window`。
- O：本次输出预留，即模型方案的输出上限。
- R：计量和协议余量，可以配置。
- B = W − O − R：实际输入上限。
- C：下一次请求的实际输入量，包括系统信息、工具 schema、记忆、摘要、原文和活动状态。C 按当前 epoch 将要发送的输入计算。
- T：上下文替换阈值，必须 ≤ B，并留出正常追加的空间。

后台压缩的启动点是 0.5 × T，即替换阈值的一半，不是窗口的一半。

### 计量

- 有对应 tokenizer 时用它计量。
- 没有时，按字节估算，并用同一模型最近请求中 Provider 报告的输入 token 数校准，再加余量。估算结果带估算器标识和版本。
- Provider 报告的用量以模型请求账本为准。估算只用于请求前的判断，不形成第二套账本。
- 每条记录的估算值缓存起来。新增事件只计算新增部分，不在每次请求前遍历整份日志。
- 模型方案缺少 `context_window` 时，提示用户补充；补充前使用保守的默认窗口。

主 session 推荐窗口不低于 128K。使用更小的窗口时，在启动或切换模型时提示一次，仍可继续运行。

### epoch

- 同一 `context_epoch` 内，已采用的前缀保持稳定。新增消息、工具结果和记忆增量追加到尾部。
- 新的摘要、压缩和记忆版本等到下一次替换时才采用。
- 每次替换保存装配清单，记录具体的来源范围和派生版本，并递增 `context_epoch`。重建依赖这份清单，不保存越来越大的累计正文。
- 用户要求忘掉时，相关内容在下一次请求前不再装入，不等普通阈值。已经写下的日志不改。

## 执行 session 的压缩

### 1. 持续摘要

执行过程中，摘要始终独立运行。即使 C 远低于 0.5 × T，已完成的轮次和阶段照常生成摘要。

### 2. 达到 0.5 × T 时启动后台压缩

当 C ≥ 0.5 × T，且有新的可压缩历史时：

1. 选择已完成边界之前的历史前缀。
2. 固定截止位置、来源范围和已有的摘要版本。
3. 提交一个有界的后台压缩请求（维护请求）。
4. 前台继续执行，当前上下文不变。

压缩输入可以包含上一版压缩结果、其后已完成的摘要和必要的原文。压缩只覆盖到固定的截止位置。压缩输入必须放得进所用模型的输入上限；放不下时，只压缩到能放下的位置。

压缩记录：`compression_id, version, session_id, base_context_epoch, source_ranges, covered_through, input_summary_refs, previous_compression_ref, text, evidence`

- 只有完整生成、来源有效且符合体积要求的结果才发布。
- 同一 session 同时最多一个活动压缩任务。
- 同一来源范围不会因为每次请求都超过 0.5 × T 而重复提交。进入新 epoch 后，出现新的可压缩历史时再启动下一次。

### 3. 达到 T 时本地装配

当 C ≥ T 时，程序构建下一版输入：

固定上下文与当前工作状态 + 已完成的压缩内容 + 压缩截止点之后已完成的摘要 + 尚未被摘要覆盖的原文 + 当前活动交换。

规则：

- 使用覆盖范围合适的最新可用压缩结果。
- 从压缩末尾往后，优先用阶段摘要，其次用轮次或分段摘要。没有摘要的范围保留原文。
- 显式保留最新的用户修改、当前目标、未完成的工具交换、活动 cell 状态、未解决事项和 `outcome_unknown` 状态。
- 同一来源区间只采用一种表示，避免压缩、摘要和原文重复。
- 一份摘要跨越压缩截止点时，不整份拼上；优先用可拆开的子摘要，拆不开时用该范围的原文。
- 系统指令和能力说明属于固定上下文，不进入摘要或压缩。

装配检查来源覆盖、版本、工具配对和实际输入预算，通过后切换 epoch。这一步是程序本地处理，不调用模型。

装配接在现有的请求准备链上（`AgentHooks::prepare_request` 和 Runtime 生成 Provider 输入的投影），不另建第二条路径。

### 4. 晚到和缺失

- 最新压缩没完成时，使用上一版可用压缩。
- 从未压缩过时，使用已完成的摘要加未摘要的原文。
- 某段摘要没完成时，保留该段原文，不算已覆盖。
- 替换之后才完成的版本，留到下一次替换。

例：T = 100K。50K 时后台开始压缩到位置 A，前台继续运行到 100K。已发布的压缩覆盖到 A，摘要覆盖 A 到 B，B 之后只有原文。新上下文就是“压缩到 A 的内容 + A 到 B 的摘要 + B 之后的原文 + 当前状态”。不要求压缩追到 100K，也不为此等待一次新的模型调用。

### 5. 硬容量出口

每次请求都检查 B：

1. 装配后仍超出预算时，先把已可靠保存的大工具正文换成有界摘录和引用，再检查。
2. 仍然超限时，暂停下一次模型请求，在有界时间内等待已经存在的后台任务。
3. 等待到达时限或结果仍不够时，返回明确的容量状态，保留任务进度。

单条用户输入本身超过可用预算时，请用户分段或改为可检索的附件。普通历史不会被静默删除来掩盖超限。

## 主 session 的淘汰与查询

### 三层上下文

| 层 | 内容 | 加载方式 |
| --- | --- | --- |
| 基础记忆 | 用户基本情况、长期目标、重要关系、稳定事实、工作目录概览 | 常驻，小而结构化 |
| 用户偏好 | 沟通方式、工作方式和持续偏好 | 常驻，小而结构化 |
| 滚动查询记忆 | 近期对话原文、相关工作的 brief、按需取回的历史 | 随当前消息变化 |

主 session 的对话同样生成轮次和阶段摘要，但不运行累计压缩。

### 预取与查询

每条用户消息接纳后，程序按明确引用、正在讨论的 WorkItem、时间范围和关键词做一次有界预取。模型还可以通过 CodeMode 继续查找摘要、brief 和原文。

检索顺序：

1. 当前明确关联的工作和近期轮次。
2. 相关的阶段或轮次摘要。
3. 必要的原始事件。

检索条件包括状态、时间、工作关联、内容类型和关键词。先用索引和关键词；是否增加向量检索，由真实召回评测决定。预取让常见上下文及时出现；查询处理“上次那个”“当时为什么这么决定”这类需要回查的问题。

### 达到 T 时淘汰

主 session 达到 T 时，程序保留基础记忆、偏好、当前请求和活跃的工作状态，淘汰较旧的原始轮次和已用完的查询结果。

- 优先淘汰已结束、最久未引用的内容。
- 当前请求、尚未处理的用户输入，以及记忆写入器尚未覆盖的用户轮次继续保留。
- 未配对的工具调用和 `outcome_unknown` 状态不淘汰。
- 被淘汰的内容仍在日志和摘要索引中，可以查回。
- 淘汰不调用模型。

装配清单：`session_id, context_epoch, base_memory_version, preference_version, retained_source_ranges, retrieved_item_refs, task_state_version`

### 记忆更新

基础记忆或偏好有新版本时，先作为尾部增量加入当前上下文，立即生效。下次更换 epoch 时，再合并进常驻部分。

工作目录只保存标题、状态、等待项和引用。详细进展通过 brief 查询。

## 基础记忆与偏好

### 存放

- 每条记忆或偏好是 `~/CodeAsYouWish/memory/` 下的一个文件。这是这些条目唯一的权威位置。
- 文件头保存 `entry_id, kind, source_type, source_log_ids, status, updated_at`，正文是条目内容。条目版本是文件内容的摘要值。
- `source_type` 取 `stated`（用户明确说过）、`inferred`（从用户的对话推断）或 `user_set`（用户直接设置或编辑）。
- 它们是可以单独增删改的条目，不是每轮重写的长篇画像。

### 记忆写入器

- 记忆写入器读取新增的、来源是用户输入的对话，生成带出处的新增、更新和停用操作。程序核对每项出处都来自用户输入，再写入文件。
- 执行结果、网页和工具输出不能直接成为记忆或偏好的来源。
- 主 session 工作区的文件能力对 `memory/` 只读，模型不能直接写入。用户在对话中要求修改或忘掉时，由记忆写入器按这条用户消息处理。忘掉只是以后不再使用，不擦日志。
- 用户可以用编辑器或界面直接查看、修改和删除条目。程序下次读取时发现内容摘要变化，就追加一条变更事件，并把条目记为 `user_set`。
- 记忆写入器写文件时带上读取时的内容摘要。文件在此期间被改过，就不写入，只保留候选。`user_set` 条目不被后台覆盖；需要更新时保留候选，由用户决定。
- 相邻的短轮次合并处理。纯确认类消息直接跳过。推断条目带出处和较低权重；明确表述优先。

### 体积

常驻的基础记忆和偏好分别设预算。超出时依次：

1. 合并重复条目。
2. 停用被新事实明确替代的旧条目。
3. 把低频细节改为不常驻、但可以查询的条目，保留出处。

用户设置的重要条目和当前有效的约束优先常驻。放不下的细节转为目录和查询入口，不直接丢弃。

偏好用于相处和做事方式，不能代替当前工作的目标、范围和用户最新的指令。

## WorkItem 与主 session 协作

### 工作边界

用户可以一直和主 session 对话。独立目标建立 WorkItem；持续的工作复用已有 WorkItem。闲聊和一次性问答由主 session 直接处理，同样记录和摘要，不强制建立 WorkItem。

### 存放

- WorkItem 保存在主 session 工作区的数据库中。
- 被派工的工作区只在自己的 Task 上记录 `work_id` 和 `dispatch_key`，用于防重和对账，不保存 WorkItem 本身。
- 主 session 与其他工作区之间的读取、派工和事件，都经唯一 Client 路由。

### 字段

`work_id, owner_main_session_id, title, goal, acceptance_criteria, acceptance_records, user_source_refs, action_scope, approval_refs, session_refs, task_refs, artifact_refs, lifecycle, waiting_conditions, pending_decisions, next_check_at, work_version, pause_version, stop_version`

- 原方案的单个 `workspace_id` 改为在 `session_refs`、`task_refs` 中逐项记录所在工作区，因为一项工作可以跨多个工作区。
- `action_scope` 描述工作预计涉及的范围，用于路由和展示，不构成放行。
- `approval_refs` 只用于审计和展示，不构成跨 Task 的放行。放行仍按 Task 和 Attempt 的精确授权，Task 结束或更换 Attempt 后失效。
- `lifecycle` 只有 `open`、`paused`、`completed`、`cancelled`。执行中、等待事件、等待用户输入、受阻、需要核对、等待交付等界面状态，由 Runtime 状态和等待记录组合得出。

### 验收

- `acceptance_records` 的每条记录包括：对应的验收条件、结果（通过、未通过、未知）、证据引用（`log_id`、产物、测试结果）、写入者和版本。
- 程序可以检查的条件，在建立 WorkItem 时就固化为可核对的检查（文件内容、实际任务状态或已有 CodeMode 执行结果）。程序观察该检查，模型只提供条件，不能把任意工具结果映射成某个条件的通过。
- 无法固化为可执行检查的条件，由主 session 询问用户，按用户的回答写入。
- 模型或执行 session 自己说“完成了”，只作为提示，不能写入“通过”。
- 所有条件都有“通过”记录时，WorkItem 才能变为 `completed`。
- Task 完成表示一次执行结束；Session idle 表示当前没有运行。两者都不代表 WorkItem 完成。
- 终态 Task 不重新打开。需要继续时建立新 Task，通常复用同一个执行 session。

### 路由

- 有明确的工作引用、当前讨论的关联或唯一匹配时，直接路由。
- 模型可以提出归属，Host 校验引用是否仍然有效。
- 无法判断是修改旧工作还是新建工作时，询问用户。

回答工作细节分三档：

1. brief 足够时直接回答，并按前沿判断新鲜度。
2. 需要核对事实时，读取摘要或原始事件。
3. 需要继续推理或操作时，委托执行 session，主 session 接收并交付结果。

主 session 不运行长时间的工作区操作，也不长期占用模型名额。一般补充在模型请求边界注入；取消和暂停走控制路径，立即生效。

### 结果回流

执行 session 返回结构化结果：完成内容、验收结果、验证证据、产物引用、未解决事项、是否需要用户输入，以及来源事件。同一工作的密集更新先合并，再进入主 session。主 session 交付结果的 Task 由程序发起，并记录来源。

## 审批

审批针对单个操作，独立于操作是否执行成功、WorkItem 是否验收通过。本地 Client 使用 `ApprovalMode::ModelAuto`；显式 SDK Runtime 默认为 `ApprovalMode::Explicit`，调用方可显式选用自动模式。

### 模型 auto 路径

模型仍只通过 `execute_code` 执行操作。原 cell 等待许可时，模型用 CodeMode 的 `approval.pending` 读取本次 Task 的待审批操作，再用 `approval.decide` 对原 `approval_id` 选择 `allow_once`、`allow_task` 或 `deny`。决定沿用原授权和持久记录，来源记为模型自动审批；随后继续等待原 cell，不重新执行脚本。

能力申请使用独立的 `request_id` 和 RequestStore。`capability.decide` 通过现有评估、批准或拒绝路径完成决定，不把 `request_id` 当作 `approval_id`，也不将普通操作批准写成能力申请批准。

自动审批能力本身不再等待一次人工许可，避免审批工具递归等待审批。本次 Task 的身份由调用上下文提供，不根据语义相近的参数代填。模型审批不自动使 WorkItem 验收通过，用户主观验收仍记录用户的实际回答。

### 显式模式与规则

`Explicit` 模式保留 SDK 和 UI 的现有逐操作决定接口。设备规则仍可按实际能力名及参数预授权；没有规则时不将“模型发起操作”直接当成“Host 已批准”。本地自动模式由模型明确执行审批步骤，不增加必须人工回答的默认流程。

Git 恢复点与审批分开：快照用于误删误改后的恢复，是否存在完整快照不决定模型能否审批文件操作。执行、取消和清理继续记录实际状态，不将未知结果伪装成另一状态。

## Git 恢复点

Git 恢复点用于在误删、误改后恢复文件，默认开启，可以按工作区关闭。建立恢复点本身不需要审批，也不作为副作用等级。快照覆盖范围只说明哪些文件能够恢复，不控制操作是否放行。

### 私有快照仓库

- 每个工作区使用一个 CAYW 私有的快照仓库，放在 `<CAYW_HOME>/workspaces/<目录摘要>/` 下；工作树就是工作区目录。
- 不在用户目录创建 `.git`，不读写用户自己的仓库，因此不改变用户的分支、暂存区和提交历史，也不受用户仓库形态（linked worktree、SHA-256、sparse checkout 等）的限制。
- 恢复点由程序内部用固定命令创建，不作为模型能力，也不向模型开放通用 Git 命令。
- 快照遵循工作区中的 `.gitignore`。`.git`、`.cayw-workspace`、`.cayw-worktrees`、`.cayw-host-lock`、`.cayw-host-read-fence`、`.cayw-host-read-state`、`.cayw-host-read-fault`、`.cayw-host-read-faults`、`.cayw-host-tmp-*` 和 `.cayw-host-read-state-*` 不进入快照。工作区包含 `CAYW_HOME` 或私有快照仓库时，这些目录也不进入快照。恢复不得覆盖这些名字。

### 何时建立

- 工作区首次接入时，建立第一份恢复点，包括已有的、未被忽略的文件。建立前先计算总字节数和文件数；超过上限时，不建立声称覆盖全部文件的恢复点，把超出的文件标为不在恢复范围内，并用本地备份保护即将修改的文件。
- 每个 Task 第一次修改工作区之前，建立一份恢复点，包括用户尚未提交的修改。
- 变更批次、构建、测试等可能一次改写多个文件的操作之前，建立恢复点。
- 恢复之前先建立恢复点，因此恢复本身也可以撤销。
- 内容与上一份恢复点相同时，不重复建立。
- 恢复点在共享工作区锁内建立，并记录在对应的调用上。建立失败时发出警告，改用本地备份保护本次要改的文件；备份也失败时，这些文件视为不在恢复范围内。

### 恢复范围

恢复范围指能进入快照或本地备份的内容；审批规则中的“恢复范围内的文件”按本节判断。

- 被忽略的文件、超过大小上限的文件和嵌套仓库中的文件不进入快照。程序修改或删除它们之前，先把旧内容存入本地备份（有容量上限）。
- 既没有快照也没有备份的内容，界面明确显示为“不在恢复范围内”。改写或删除这类文件要询问用户。

### 没有 Git 时

- 检测不到可用的 Git 时，发出警告，继续工作。警告在打开工作区时显示一次，`cayw doctor` 也会报告。
- 检测 Git 时不能触发 macOS 的命令行工具安装弹窗。macOS 的 `/usr/bin/git` 在命令行工具未安装时会弹出安装对话框，因此不能直接执行它。检测前先确认开发者目录已安装（例如 `xcode-select -p` 指向的活动开发者目录下存在 `git`），只在确认后才执行。
- 没有 Git 时，程序仍在修改或删除文件前保存本地备份；只是无法为整个工作区建立恢复点。

### 恢复

- 只能从 CAYW 自己的恢复点恢复，不能按模型给出的任意提交恢复。
- 按文件或变更范围恢复，不盲目恢复整棵目录树。
- 逐个文件核对：恢复点之后被他人改过的文件（包括用户和其他 session），不直接覆盖，先询问用户。
- 恢复先写意图记录。中途中断的文件记为 `outcome_unknown`，核对后再处理。
- 恢复与进行中的变更批次互斥。

### 保留

恢复点建立之后留着。程序不按数量、大小或期限自动删除，也不回收旧对象。体积计入存储指标，只用于显示。

关闭 Git 恢复后，不再建立恢复点和本地备份，CodeMode 入口和审批规则不变；删除已有文件因此都会询问。

## 输入、派工与主动工作

### 事件信封

`event_id, source, source_event_id, workspace_id, work_id, session_id, kind, occurred_at, received_at, origin, payload_ref, source_cursor`

按 `(source, source_event_id)` 去重；先保存事件，再推进来源游标。去重记录至少保留到来源不可能再次投递为止。同一事件重复接收，只形成一次有效输入。

### 输入四态

| 状态 | 含义 |
| --- | --- |
| `received` | 已持久保存原始输入 |
| `attached` | 已确定归属的 session 或 WorkItem |
| `included` | 已进入某次模型请求的输入清单 |
| `handled` | 已有处理结果、转交记录或明确的结束结果 |

输入身份就是原始输入事件的 `log_id`；状态变化作为事件追加，不另建 Inbox。`included` 不等于已经处理完。

运行中的一般补充先写入日志，再在下一个模型请求边界进入模型。steer 只是低延迟的投递方式；恢复时以日志为准。

每个 Session 同时只有一个活动 Task。需要并行时，使用独立的 Session。

### 幂等派工

- 派工前，主 session 记录派工意图，并生成稳定的 `dispatch_key`。
- 目标工作区创建 Task 时，在同一事务内保存 `dispatch_key`、`work_id` 和输入摘要；`dispatch_key` 唯一。
- 相同 key、相同输入，返回同一个 `task_id`；相同 key、不同输入，返回冲突。
- 响应丢失时先按 key 查询，不再次创建。
- 这只保证派工不重复建任务。任务内部的外部动作仍各自记录结果和幂等标识。

### 主动模式

主动模式与审批规则分开配置：

- `off`：不从环境变化推断新工作；用户已经明确请求的工作照常执行。
- `observe`：读取变化、整理证据、形成建议。
- `auto`：针对有效的工作或具体规则，自动判断并推进下一步。

主动模式不改变审批规则：放行规则内的操作照常放行，需要询问的操作照常询问。

触发来源包括已有义务的续办、用户明确要求的监控，以及环境变化带来的候选工作。候选工作先形成目标和证据，再按主动模式决定只展示建议，还是进入执行。普通文件变化不直接等同于新任务。

自动规则记录来源、条件、目标、动作范围、工作区、频率、有效时间和通知方式。执行前核对：工作仍有效；条件仍成立；同一变化尚未处理；没有同一操作在运行；输入版本符合。

主动规则的用量记录和派工意图写在同一个持久事务里，只记录一次。派工失败时保留为待核对，不重复派工。并发触发按 `(rule_id, condition_version)` 合并。

按 `(rule_id, work_id, condition_version)` 合并同一批变化。设置并发、重试和频率上限。自身写入产生的文件事件通常只更新当前工作状态，不重新触发同一规则。

### 唤醒

使用事件驱动加到期索引扫描。只唤醒有新增事实、到期检查或未完成义务的工作，不为每个历史 session 常驻一个 Worker。

摘要发布、Dream 完成和普通引用维护默认不唤醒用户对话。发现需要推进的工作时派工；发现值得通知的结果时，交给主 session 合并交付。

## 沟通、通知与工作控制

### 用户沟通

用户提出请求或更正后，主 session 及时回应，不等后台维护完成。进展只围绕有用的阶段成果、计划或时间的变化、实际阻塞、需要的业务信息和最终交付。

单个工具步骤、摘要完成、无变化的检查和重复失败不单独通知。非紧急更新合并发送。主动提醒发送前重新核对：事实仍成立；用户尚未处理；同一变化尚未通知。

### 通知记录

`notification_id, work_id, work_version, target, content_ref, artifact_refs, status, receipt_ref, created_at, updated_at`

- 发送前保存意图（`pending`）；写入本地待发队列时记录为 `queued`（`receipt_ref` 为空），不伪造送达回执；外部渠道返回真实状态后再保存回执。
- `queued`、`accepted`、`sent`、`delivered`、`read` 分开记录，回执只使用外部服务实际提供的状态。
- 结果不明时先查回执，不直接重发。
- 工作完成与交付成功分开记录。产物已完成但交付失败时，保留待交付项，不重新计算。

### 暂停、取消、停止和恢复

- 取消本次执行：作用于当前 Task，按现有的完整取消路径执行，保留 Runtime 的 detached 语义。
- 暂停工作：保存暂停版本，停止新的派工。`pause_version` 和 `stop_version` 写进派工 Task，并由 Client 在版本变化时推送到目标工作区。目标工作区的 Host 在每次能力调用前核对 Task 上的当前版本，暂停后的新调用不执行；当前 Task 在下一个模型请求边界停止，继续位置保存在 WorkItem 中。已经开始的动作记录实际结果。
- 停止整项工作：保存停止版本，经 Client 推送到各目标工作区，取消待派工、到期监控和属于该工作的全部 Task。
- 恢复或重新打开：由用户的新决定产生新版本，再按当前事实继续。

暂停或取消后，晚到的结果仍写入事实，但不自动重新派工。清理未完成、动作结果未知和通知未确认分别保留，界面显示真实状态。

## 维护请求与后台调度

摘要、压缩、Dream 和记忆写入器都需要在后台调用模型。这类调用称为维护请求。四类维护共用一个调度底座，各有自己的任务类型、来源范围和前沿。用量记到来源预算树，不另设上限。

### 为什么需要单独的类别

现有模型请求账本有三条规则：

- 每次请求先预留同一预算树的全部剩余额度（`EntireSessionRemainder`）。
- 同一预算树同时只允许一个在途请求。
- 只要树上有未结算的预留，后续请求就会被拒绝，除非有绑定新 Task 的延续授权。

本设计不设用量上限，因此不再有“全部剩余额度”可以预留。后两条只约束同一棵树上的前台请求，用来记住在途用量，避免算丢或算两次。它们不是用量上限。维护请求不沿用这两条去挡住前台。维护请求中断留下的未知用量也没有 Task，无法按现有路径解除。所以维护请求仍是单独的类别。

### 规则

- 身份：维护请求不使用执行 lease。它的身份是“维护任务 + 尝试次数”，并记录来源 session、来源范围、输入版本和所用模型。它只读来源 session，不占来源 session 的执行名额。
- 记录：维护请求记在来源工作区数据库中单独的维护记录里。维护请求不持有来源 session 的活动 lease；来源运行时不能匹配当前 attempt 和 cursor，也不能改写来源 session 的投影，所以不写入来源 session 的 Core 事件。空闲 session 可以不带 lease 追加控制事件，但本设计仍选择单独记录，以保持用户会话的事件前沿和摘要输入不变。它复用 Provider、取消和错误处理。
- 预留：每次只记下这次调用的用量上界，即输入的 UTF-8 字节数（作为 token 上界）加协议余量，再加输出上限。这是记账，不是限额。不预留整树余额。
- 记账：维护用量记到来源预算树，只记录，不设单次或累计上限。
- 锁：维护请求只在预留和结算时短暂使用该树的预算锁，不在请求期间持有。前台请求在途时持有这把锁，维护请求等它结束后再预留。
- 准入：维护的在途预留和未知用量不挡住前台请求。这些用量仍计入合计，但不算作需要延续授权的未结欠账。维护请求在途时，前台请求照常准入。
- 未知用量：维护请求结果不明时，原预留继续占用并计入合计，不按零计算。维护请求没有执行 lease，也没有对应 Task。现有 `reconcile_model_request` 按 `request_id` 查找来源 session 的模型请求账本，并要求记录带执行 lease 和对应 Task，还要校验 Task 的 attempt 和 worker 一致，因此维护请求不能直接复用。维护请求使用独立的核对入口，按维护记录、尝试次数和来源预算树核对，由可信核对者确认实际用量；核对后写入维护记录并释放对应预留，不需要延续授权。维护请求不阻塞前台。
- 超额报告：Provider 报告的用量超过预留时，按报告值记录并标记超额，不判为账本损坏。现有 `reconciliation_tokens` 把超过预留的报告判成无效报告，维护核对入口不沿用这条规则，自行处理超额。
- 维护请求不新建 session。

### 调度

- 前台请求优先。压缩接近替换阈值时提高优先级。摘要、记忆写入和 Dream 保留最低的调度机会，或随等待时间提升优先级，避免长期得不到执行。
- 相邻的小范围可以合并调度，但保留各自的来源和轮次边界。
- 同一 session 同时最多一个活动压缩任务；摘要可以并行，按来源区间发布，并推进前沿。
- Provider 只允许串行时，后台只利用空闲间隙，不宣称能同时运行。
- 维护失败或积压时保留原文，并显示维护积压。
- 维护模型默认使用来源 session 所选的模型。也可以分别为摘要、压缩、记忆写入和 Dream 选用设备模型列表中的其他模型。

### 积压

各类维护记录待处理量、最早待处理时间、失败次数和前沿。达到告警值时，降低非必要维护的频率，或进入保留原文的降级状态。

没有新内容的历史 session 不产生维护任务。索引和 token 估算增量更新；摘要发布不重写大日志。

## Dream、来源与忘掉

### Dream

Dream 整理已有摘要的出处和引用结构，不改写原始日志，也不代替摘要器或压缩器。它只处理已逻辑封口的范围：

- 按引用类型组织。
- 列表内去重。
- 把重复的上层引用下沉到合适的子摘要。
- 把过长的直接引用表转为可以展开的次级引用。
- 只在有明确替代关系时设置 `superseded_by`。

整理后，结论到原文的路径必须保留，下沉可以还原。每次发布新版本；已被采用的版本保持不变。

### 来源

每个内容对象保留 `origin` 和 `source_log_ids`。用户输入、Runtime 事件、工具返回和外部内容分别标记。经过摘要、压缩或跨 session 转述后，仍能找到最初的来源和实际的确认状态。

### 忘掉

用户说忘掉某段内容后，以后的回答、摘要、压缩和记忆不再使用它。

- 忘掉本身追加为一条新记录，写明不再使用的来源范围。原来的事件不改、不擦。
- 下一次模型请求前，装配、预取、新的摘要、压缩和记忆都跳过这个范围。已经发布的摘要和压缩留在磁盘上，但不改写，也不再装入。
- 按游标读取日志仍返回原来的事件。不在读取接口上隐藏。
- 不追查插件、导出、恢复点和已经复制出去的副本。
- 用户自己编辑或删掉 `memory/` 里的文件，按文件的当前内容读取。这是用户改自己的文件，不是清除日志。

## 恢复与一致性

重启后，先运行现有的 `Runtime::recover` 流程，再按顺序处理新增部分：

1. 恢复 Runtime 的 Task、Session、活动状态和预算账本（现有流程）。
2. 确认日志的完整前沿。
3. 对账 WorkItem 与各工作区 Task、Session 的持久关联，不依赖内存中的 FleetView。
4. 对账输入四态和派工意图，按 `dispatch_key` 找回已经创建的 Task。
5. 核对没有最终结果的动作：有可靠证据的按证据追加结果，无法确认的保持 `outcome_unknown`。
6. 核对通知意图和回执，恢复待交付项。
7. 校验摘要、压缩、brief、记忆和装配清单的来源与版本；只校验恢复时要用到的部分，其余在使用前校验。
8. 只为仍然有效的工作和规则重建到期事件。
9. 通过 brief、增量事件和保存的装配清单继续执行。

恢复不重放旧的脚本栈。文件操作查询实际文件；远端动作查询服务状态；用户要求和历史决策读取原始记录。无法确认的结果保持未知，由后续核对解决。

账本有引用但原始内容缺失时，保留待核实状态。来源不完整的派生结果不当作完整事实。

## 模块位置与存储

| 部分 | 位置 | 说明 |
| --- | --- | --- |
| 原始事件、Session、执行事实 | Core（现有） | 不变 |
| WorkItem、输入状态、派工意图、询问与通知记录 | 主 session 工作区的会话事件，加 Runtime 维护的查询表 | 查询表可以从事件重建 |
| Task 的 `work_id`、`dispatch_key` | 目标工作区 Queue 的 Task 表 | 与 Task 创建在同一事务内；`dispatch_key` 唯一 |
| 维护请求记录 | 来源工作区数据库中的维护记录 | 账本投影同时读取 Core 事件和维护记录；预算视图、核对和延续授权都使用同一份投影 |
| 放行规则 | 设备级、模型不可写的用户配置 | 由 Client 维护版本，派工时随 Task 下发 |
| 摘要、压缩、brief、装配清单、token 估算 | 上下文模块自己的表 | 派生数据，可以重建 |
| 基础记忆与偏好 | `~/CodeAsYouWish/memory/` | 用户可以直接查看和编辑 |
| Git 恢复点、本地备份 | `<CAYW_HOME>/workspaces/<目录摘要>/` | 私有快照仓库 |
| 设备模型列表 | `<CAYW_HOME>/models.json` | 替代每工作区 `models.json` |

### 上下文模块

- 上下文模块是 Runtime 的内置组件，不是 plugin。每次模型请求前都要经过它，还要保证工具配对和未知状态不丢；plugin 接不进这一步。
- 纯计算部分（摘要结构、装配算法、覆盖检查、token 估算）放在 `cayw-context`。调度维护请求、保存派生记录和接入请求准备链，由 `cayw-runtime` 负责。
- 路线图原有的“Core 基础压缩”就是这个内置组件。这里的“Core”指 Headless Core 产品边界，不是 `cayw-core` 包。JEv plugin 只能提供由 Runtime 选用的增强压缩实现，不能接入请求准备链或替换装配步骤；增强压缩失败时回退到内置压缩。

### 主动工作模块

- 主动工作模块负责事件接入、规则、到期索引、候选工作和通知合并。它是可以关闭的 Runtime 组件；主动模式为 `off` 时不运行。外部事件适配器按 plugin 接入。
- 派工始终使用现有 Runtime，不另建队列、lease 或资源账本。
- 关闭后，普通 Runtime 和 CodeMode 继续工作；已登记的工作、未确认的派工和待交付项保留，可以继续查看和处理。

### 存储版本

- 优先使用 Core 已有的宿主扩展事件保存新事实，不改 Core 格式。现有模型请求账本就是这样保存的。
- 新增结构直接使用当前存储格式，不为不存在的旧版本添加迁移或兼容读取。
- IPC 帧协议 v1 不变；新增的方法按 [SDK/IPC 契约](issue1-sdk-ipc-contract.md)增加。

## 参数

| 参数 | 起始值或规则 |
| --- | --- |
| 主 session 目录 | `~/CodeAsYouWish`，可以在设备配置中覆盖 |
| 设备模型列表 | `<CAYW_HOME>/models.json` |
| 模型上下文窗口 W | 模型方案的 `context_window` |
| 主 session 推荐窗口 | 不低于 128K；更小时提示一次 |
| 替换阈值 T | 按模型的实际输入上限 B 配置，T ≤ B |
| 后台压缩启动点 | 固定为 0.5 × T |
| 长轮次分段启动 | 未摘要增量约 4K token 后，寻找完整边界 |
| 分段目标规模 | 约 8K token，可以因完整边界略有变化 |
| 大结果独立分段 | 约 8K token 以上 |
| 压缩并发 | 每个 session 1 个 |
| 大结果自动外置 | `auto_externalize_threshold_bytes`，默认 32 KiB，与 token 预算分开计量 |
| 替换后的目标大小 | 可以设低水位，按 T 或 B 的比例显式配置；不是替换成功的必要条件 |
| 硬容量等待 | 有界、可以配置；超时后保留工作状态，返回容量结果 |
| 维护模型 | 默认使用来源 session 的模型；可以为四类维护分别选用其他模型 |
| 维护用量 | 记到来源预算树，只记录，不设上限 |
| 主动模式 | `off` / `observe` / `auto` |
| 审批 | 放行规则加主 session 询问；默认规则见“审批” |
| Git 恢复点 | 默认开启，可以按工作区关闭；建立之后不自动删除 |
| 忘掉 | 以后不再使用；日志留在磁盘上，不擦除 |

4K、8K 是内容分段的起始参数，不定义用户轮次，也不是工具输出的字节上限。低水位和模型选择按实际评测调整。

## 验收与评测

离线管道测试与真实模型评测分别运行。真实模型调用需要当次授权。关键回归不得退化。

### 上下文与维护

1. 未到 0.5 × T 时，已完成的轮次照常生成摘要；到启动点时独立运行压缩；到 T 时本地装配，不新增模型调用。
2. 装配准确包含压缩覆盖的内容、其后已完成的摘要和未摘要的原文，没有来源缺口或整段重复。
3. 摘要和压缩使用固定的来源范围；新内容不会混进正在生成的快照。
4. 乱序完成不会跳过前沿；旧版本不覆盖新状态；晚到的版本留待下一次采用。
5. 替换后，工具配对、活动 cell、游标、取消和 unknown 状态保持正确。
6. 大输出保存失败时不产生虚假引用；超过 B 时不发送超限请求。
7. 主 session 到阈值时只淘汰；历史可以通过摘要和原文查回；记忆写入器尚未覆盖的用户轮次不会提前离开上下文。
8. 维护请求在途或结果未知时，前台请求照常准入；维护不在请求期间持有预算锁，不预留整树余额，用量计入来源预算树；没有新内容的 session 不产生维护任务。

### 记忆与来源

9. 闲聊、工作和历史决策都能按范围检索，原始出处可达。
10. Dream 去重和下沉引用后，结论仍能追溯到原文。
11. 用户直接编辑的记忆立即生效，标为 `user_set`，后台不覆盖；推断来源可见；工具输出不能成为记忆的来源。
12. 用户说忘掉之后，以后的回答、摘要、压缩和记忆不再使用那段内容；按游标读取仍返回原来的事件；已经写下的日志保持不变。
13. 主 session 的身份不因压缩、淘汰、重启或模型切换改变。

### 工作与执行

14. 所有模型执行都经过 `execute_code`；没有另一套通用命令入口。
15. 本地模型通过 CodeMode 自动决定原操作；普通审批与能力申请使用各自真实 ID 和决定接口，不要求额外人工审批。审批结果不能代替执行结果或用户验收。
16. 首次接入的恢复点可以恢复误删的文件；后续恢复点可以恢复用户未提交的改动；用户仓库的暂存区、分支和提交历史不变；恢复前先核对恢复点之后他人所做的修改，不直接覆盖，需要覆盖时先询问用户；没有 Git 时显示警告，工作继续。
17. 重复事件只形成一次有效输入；收到输入后崩溃可以恢复；`included` 不会被当成 `handled`。
18. 派工响应丢失后，按 key 找回原 Task，不重复创建。
19. 暂停和取消在控制路径生效；晚到的结果、文件事件和旧计划不会重新启动已停止的工作。
20. Task 结束与 WorkItem 完成区分开；工作完成与通知送达区分开；模型自报不能写入验收“通过”。
21. 通知结果未知时查询回执，不盲目重发；关闭主动工作模块后，工作记录和待交付项仍然可见。
22. 设备模型列表被所有工作区共用，各工作区独立选用；不读取旧模型配置或进行迁移，密钥不回显。

### 模型效果

持续运行长对话和长任务回放，强制经历多次上下文替换，检查：

- 早期要求是否保留，修改后的要求是否优先。
- 历史事实、决策原因和出处能否回查。
- 多次压缩后信息是否衰减，哪些内容需要靠原文检索补回。
- “上次那个”能否找到正确的工作。
- 记忆是否符合用户的表述，用户纠正后是否生效。
- 主动触发是否有实际价值，是否重复打扰。
- 暂停、取消、恢复及中断后的动作是否符合真实状态。

### 指标

- 前台请求准备、装配和容量等待的耗时。
- 摘要、压缩、记忆写入和 Dream 的调用数、token、滞后和失败率。
- 替换前后的大小、间隔和缓存命中变化。
- 输入的遗漏率、重复率、错归属率和过期触发率。
- 通知的有用率、打扰次数，以及唤醒后确实有事的比例。
- unknown 的核对情况。
- CPU、内存、I/O、空闲负载和各类存储体积（包括恢复点和备份）。
- 前后台总 token、未知用量和费用未知的请求数。现有模型方案没有价格字段，费用无法确认；以后增加价格来源，再统计费用。

目标是让主 session 保持可响应、工作能够持续推进、历史可以找回、上下文替换不丢关键状态。主动消息数量和压缩次数本身不作为成功指标。
