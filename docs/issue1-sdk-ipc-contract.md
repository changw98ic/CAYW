# Session SDK and IPC contract

This is the local Issue [#1](https://github.com/changw98ic/CAYW/issues/1) delivery contract. The executable downstream examples are in [`examples/issue1-client`](../examples/issue1-client/README.md). They use the public `cayw_runtime::Runtime`, `cayw_core::SessionStore` and `cayw_ipc::Client` interfaces. The runtime graph needs no UI, optional Server, VerifyTool, Codex or external code index. All model responses in these examples are fixed local fixtures; real Host file operations, SQLite commits and loopback TCP remain in the execution path.

## Identity and persistence

A Session is a durable conversation with a stable `id`. Its history, ordered events, approvals, original calls and execution facts survive a process exit. A Task is one explicit prompt admitted to the durable Runtime queue. An Attempt is one fenced execution of that task. A Worker is the replaceable executor identified by `worker_id`; it is not the Session and its identifier is not the operating system PID. Each attempt lease contains `session_id`, `attempt_id`, `worker_id` and the monotonically increasing `fence`. Core checks the complete lease in the same transaction as an execution write.

The canonical store is SQLite, Core protocol/schema v3. Events and the current projection commit together. Each event retains its Session, cursor, timestamp, Core version and original attempt lease when applicable. Capability records additionally retain the task, execution, parent model call, source hash, capability name, exact arguments, sequence, authorization and terminal outcome. Core capability sequence starts at zero; Cells intent sequence starts at one and conversion checks the boundary.

Opening a store or Runtime does not claim an old worker, replay a prompt, or restart a VM. `Runtime::recover` is explicit and checks that the original task/Cells execution ownership can be held exclusively. Pending Device cleanup must also be confirmed. Only then can recovery fence old leases, repair durable projections and release the task reservation. A process kill in the example is followed by `Child::wait` and exit-status inspection before reopening. This demonstrates process-exit recovery; it does not simulate sudden power loss.

The original Issue comment proposed JSONL storage and Unix sockets/Windows named pipes. That implementation sketch has been superseded by the existing SQLite Core v3 store and authenticated loopback TCP IPC v1. There is one current path; this delivery does not introduce a parallel JSONL or socket implementation.

## Public calls

The downstream `sdk` mode constructs `Runtime::open` with an explicit workspace, database, model, Provider and `RuntimeConfig`. It calls `create`, `prompt`, `wait_events`, `approve`, `cancel`, `tasks`, `get`, and reads actual Core events through `events`. No client accesses private Runtime fields.

The IPC handler uses the same Runtime implementation. Important method mappings are:

| IPC method | Public Runtime operation | Result |
| --- | --- | --- |
| `session.create` | `create` | `SessionView` |
| `session.get`, `session.list` | `get`, `list` | Current durable view(s) |
| `session.prompt` | `prompt` | View after this request stops |
| `session.events` | `wait_events` | Ordered `EventRecord` page |
| `session.cancel` | `cancel(&CancelTarget)` | `{cancelled: bool}` |
| `approval.decide` | `approve` | Original `ApprovalRequest` with decision |
| `session.tasks`, `task.get` | `tasks`, `task` | Durable task identity/state |
| `task.enqueue`, `task.resume` | `enqueue`, `resume` | Explicit queue admission/execution |
| `task.enqueue_with_intent` | `enqueue_input_with_intent` | Host-recorded explicit project-test intent and admitted Task |
| `task.enqueue_scheduled` | `enqueue_scheduled` | Host-selected intent and priority on the original admitted Task |
| `runtime.scheduler` | `scheduler_page` | Bounded live-task page, execution-slot facts and persistent fairness counters |
| `runtime.resources` | `resources` | Persisted declared-memory policy, current reservations and capability matrix |
| `task.enqueue_with_resources` | `enqueue_with_resources` | Trusted Task input, intent, priority and resource declaration |

| `request.operations` | `request_operations` | Exact host-selected requestable operations |
| `request.status`, `request.events`, `request.task_state` | Same-named request SDK operations | Durable request, event page or original Task authority |
| `request.decide` | `request_evaluate`, then approve/deny/unavailable | One trusted decision for the original eligible request |
| `request.revoke`, `request.close_task` | `request_revoke`, `close_request_task` | Withdraw original authority and cancel its original Task |
| `session.recover` | `recover` | View after explicit stopped-owner recovery |
| `session.reconcile`, `capability.reconcile` | `reconcile`, `reconcile_capability` | View after evidence-based repair |

Parameters reject unknown fields. IPC approval and reconciliation actors are fixed by the host as `rpc-user`; request text cannot grant itself another actor's authority. SDK actor is trusted host input. The example uses `synthetic-sdk-reviewer` for SDK approval, and all allow/deny choices are explicitly synthetic fixture decisions, not human approvals.

Task capability requests use an additional approval authority. `capability.request` and `capability.status` are the only model-facing controls; they accept no actor, approval or Task identity fields. A trusted host can evaluate the first valid request, including an ordinary request. Repetition counts are hints and never grant authority. Trusted SDK callers select `TaskIntent::ExplicitProjectTestOrScript` when the user explicitly asks for the configured project test or script. Authenticated IPC has `task.enqueue_with_intent` with `{session_id, text, images?, intent}`; ordinary `task.enqueue` continues rejecting an `intent` field. Intent records that explicit need and does not grant permission. Tasks that never use request authority do not consume its lifetime quota. Known-ended request activity releases active admission while retaining audit records and grant invalidation.

IPC `request.decide` takes `{task_id, request_id, decision, reason}`. The tagged decision is `{"kind":"allow","lifetime_ms":N}`, `{"kind":"deny"}` or `{"kind":"unavailable"}`. The host fixes the actor to `rpc-user` and validates the reason and lifetime before claiming evaluation. It then creates the private Rust evaluation ticket and applies that one decision through the existing SDK. The ticket is never serialized or reconstructed from JSON. Evaluation and the decision remain two independent durable transitions; cancellation, expiration or a failed write between them can reject the original decision. The server never obtains a replacement ticket or automatically retries approval. Status/events retain the actual state for inspection. Decision validation uses the current durable request limits, including a trusted adjustment made after this Runtime opened.

`request.status` and `request.revoke` take the original `task_id` and `request_id`; revoke additionally requires `reason`. `request.task_state` and `request.close_task` take `{task_id}`. `request.events` takes `{task_id, after?, limit?}`; its limit is 1..64 and defaults to 64. `request.operations` takes an empty object. Revoke/close cancel the original Task through its current full cancellation identity. A dispatched effect retains its original outcome and cleanup obligation; revocation does not mean rollback. Request decisions have `request_stale`, `request_not_found`, `request_denied`, `request_budget_exceeded` and `request_policy_changed` error codes. An authority persistence failure uses `request_authority_unavailable_outcome_unknown` and requires inspection rather than an automatic decision retry. These additions describe the current API; historical Issue #1 evidence does not certify Issue #8's new scenarios.

Reconciliation requires `expected` with the complete original identity. Capability repair retains its lease, Task, execution, parent call and source hash. Model-tool repair also retains the original exact `ToolCall` and optional execution input. `RuntimeConfig::reconciliation_verifier` defaults to `None`, so a nonempty actor/evidence string cannot authorize repair. The trusted host must install a verifier that checks the actor, original receipt and proposed known outcome. Evidence remains a string interpreted by that verifier; Runtime does not infer the truth of arbitrary text. The independent process fixture verifies its synced receipt and confirmed original child exit; it rejects other repairs and never replays source. Current v3 reconciliation records without `expected` are rejected without rewriting storage; there is no weaker fallback path.

Host authorization does not override reliable local facts. Core rejects a parent launch `NotExecuted` decision when that execution already has a known completed or failed child. Runtime also checks original Cells results before committing Core, including a failed child with no result payload or digest. A later registered wait only observes an existing execution; a known child does not prove that this separate wait was dispatched. Exact retries retain the same decision and event cursor; changed identities or decisions are rejected.

Reconciliation appends the host decision and updates the execution projection. The original unknown tool result, message and event prefix remain unchanged. A subsequent Agent receives a separate continuation copy with the committed decision; it does not rerun the old source. Confirmed Fork follows a unique durable `SessionForked` origin and its fixed `source_cursor`. It checks original stored calls, messages and decisions at that cursor, including each ancestor of a later Fork. Cycles, duplicate origins, altered call results and out-of-range cursors are rejected instead of synthesizing a new original identity.

Core, Cells, Requests and the Task queue commit independently. If Core commits a reconciliation but Cells repair fails, Runtime keeps the Session frozen and rejects enqueue and confirmed Fork. Reopening does not clear that condition. After the original write failure is removed, an identical reconciliation can finish Cells repair without appending a second Core decision; another identical retry changes neither Cells nor Core. Only completed repair permits an explicit next Task or confirmed Fork. A Session frozen solely because its bound plugin is unavailable can still use its existing confirmed conversion to a new ordinary chat; this does not bypass unresolved execution facts.

Request-authority inspection and repair are host administration SDK operations. Ordinary model tools and IPC JSON do not accept a `HostActor` or authorize repair. Rotating authority revokes old grants while retaining Core and queue facts; explicit recovery is still required. These boundaries do not claim acceptance of an unexecuted repair scenario.

On macOS, `Runtime::confirm_lost_processes_stopped(store_path, config, &CancelTarget, &HostActor, evidence, verify_stopped)` is the sole host administration entry for confirming cleanup after the original process supervisor is lost. It requires the complete original Task identity and checks its original Core lease, supervisor incarnation, process records and stopped Cells scope. The mandatory callback receives `ProcessCleanupInspection`; the trusted host must independently compare the original PID, start time and process group and verify its owned resources stopped. An actor name and evidence text alone do not confirm cleanup. A live original supervisor is rejected before the callback, even when its child processes have stopped. That owner must retry its actual cleanup through `drain_task_processes`. Cleanup confirmation only records resource evidence; it does not settle unknown business effects, repair Requests, or release the Task's reserved capacity. Explicit recovery remains separate. No ordinary IPC method or model tool exposes this management operation.

## Scheduler admission and live pages

`task.enqueue_scheduled` takes `{session_id, text, images?, intent, priority}` with `priority` exactly `low`, `normal` or `high`. The trusted host supplies priority and intent. Ordinary enqueue uses `normal`. Enqueue only persists acceptance; `task.resume` explicitly claims work. Opening Runtime never dispatches it. Duplicate live work in one Session returns `busy`; full accepted capacity returns `queue_full`, without creating a Task.

`RuntimeConfig::max_concurrent_runs` is K (1..1024). `max_queued_runs` is the total live capacity C (K..100000), including queued, running, waiting approval and draining Tasks. `fairness_after_dispatches` is A (1..100000, default 8). Unpromoted ready Tasks sort by priority descending and then their durable ready order. After A other dispatches, a continuously ready Task is promoted; promoted Tasks sort by ready order before unpromoted work. When slots continue to be released, other dispatches can overtake a continuously executable accepted Task at most A + C - 1 times. New arrivals cannot enlarge that bound. Admission counters and ready positions commit with admission and survive reopening. Each readmission after approval starts a new ready round; retries while already ready keep the same position.

A Task can park in `waiting_approval` only when no model request is active, every live cell is stopped before its capability authorization boundary, and its original Host has no active process, unjoined terminal or unresolved process/terminal completion facts. A completed `exec_command` call can still own a running background process; approval for its next call keeps the original slot until that process and terminal work are safely finished. Parking keeps the Task, Attempt, Worker, fence and ownership lock while setting `holds_slot=false`. New model requests, tools and resumed capability calls all require the same Task's scheduler admission. An allow or deny decision reacquires the slot before the VM resumes; cancellation instead stops and joins original execution. `draining` retains its recorded `holds_slot` value until confirmed recovery. A Task that safely released a slot before a later bookkeeping failure keeps live capacity but cannot reserve another Task's slot.

After confirming that the old owner stopped, explicit recovery detaches a claimed queued Task that has not begun an Attempt and increments its fence. It retains the original Task, input, priority and fairness position. The Task continues occupying C but cannot participate in dispatch until explicitly resumed again. A cancelled old claim instead receives one durable cancellation terminal. Repeated recovery does not advance either terminal or detached claim again; old cancellation identities and old worker leases are rejected.

IPC `runtime.scheduler` takes `{after?: string, limit?: number}` and calls `Runtime::scheduler_page`; `Runtime::scheduler(limit)` starts at the first page. Limit is 1..1000 and defaults to 100 over IPC. The result contains `max_concurrent_runs`, `max_accepted_tasks`, `fairness_after_dispatches`, `max_bypasses`, `dispatch_count`, `tasks` and `next_after`. Tasks retain their priority, complete cancellation identity, state, error, slot ownership, ready order, ready-at-dispatch counter and per-Task dispatch count. Pages use acceptance order, not dispatch order. Pass `next_after` until it is null; an exact-size final page may be followed by an empty page. A terminal Task ID remains a valid cursor but its row is omitted from live pages. Unknown cursors and invalid limits return `invalid_params` without changing counters. Pages are live reads and do not freeze the queue across requests. IPC frame byte limits still apply; reduce the page limit when needed.

IPC `runtime.fleet` takes `{parent_session_id?: string, after?: string, limit?: number}` and returns the FleetView page (`members`, `next_after`). Limit is 1..1000 and defaults to 100 over IPC. `runtime.fleet.stop` takes `{child_task_id}` and requests cancellation of one running member. `runtime.fleet.steer` takes `{child_task_id, text}` and appends one steering user message when the child Agent control is attached. Background / detached members remain visible after the parent capability returns; parent `session.cancel` does not stop them. These methods do not create a second scheduler.

Interrupted attempts and `outcome_unknown` remain in per-Session Task/event history. The live scheduler page does not replace Session reconciliation state or Device cleanup evidence. A trusted host can amend scheduler and resource policy after safe shutdown when no active or unconfirmed-cleanup Task remains. Durable state and process-shared coordination prevent concurrent or stale Runtime instances from admitting work under conflicting policies. Reconfiguration does not clear unknown effects or release cleanup holds. These scheduler additions have their own Issue #11 validation; historical Issue #1 evidence does not certify them.

## Local resource admission and content

`RuntimeConfig::resources` and the headless JSON `resources` object fix `max_declared_memory_bytes` for all Runtime connections to one database. The positive total fits SQLite's signed integer range and defaults to 1 GiB. `task.enqueue_with_resources` takes `{session_id, text, images?, intent, priority, resources}`. `TaskResources` defaults its declared bytes to zero, meaning no reservation, not measured zero usage. Admission reserves declared bytes and `holds_slot` in the same SQLite transaction. Over-total requests fail before enqueue; insufficient remaining capacity waits at the original selected queue head. Safe approval parking releases both admission facts. Unconfirmed cleanup or persistence keeps the original reservation. `runtime.resources` takes `{}` and returns the configured policy, aggregate usage and the supported/unsupported mechanism matrix; original ownership remains on `TaskRecord`.

This policy does not measure or enforce actual process memory. CPU quotas, hard memory ceilings, GPU allocation/isolation and I/O bandwidth limits are unsupported. Any `Some` hard-memory, CPU or I/O requirement, including zero, and nonzero `gpu_units` reject before enqueue. Device process-output and elapsed-time budgets remain software execution budgets on the existing cancellation and cleanup path. Unavailable measurements are never emitted as zero.

`RuntimeConfig::content` and headless JSON `content` optionally select an absolute private directory, `device_id` and `limits`. A trusted host can enable content after an earlier disabled configuration and can increase quotas for the same bound root and Device after safe shutdown. Configuration changes coordinate with concurrent Runtime and content handles; a stale handle cannot silently use a conflicting policy. The committed binding retains the actual root device/inode and Device identity. It can commit before the rest of `Runtime::open` succeeds. Root replacement or a changed Device is rejected before candidate store initialization; a missing bound root is not recreated. Actual file operations retain the originally opened no-follow directory handle. The model workspace and content directory cannot overlap.

The model-facing `content.read` accepts `{name, scope?}` and `content.put` accepts `{name, scope?, text, expected_version, expected_revision?}`. Owners come from the original CallScope. Scope defaults to `session`; `task` means only the current Task. Names contain 1–64 ASCII letters, digits, underscore or hyphen. Paths and explicit owner fields reject. Creation uses version zero without a revision; update supplies both the exact observed positive version and 64-character lowercase revision. Model text is limited to 64 KiB of UTF-8 bytes and the store's configured content limit. Calls use the same Host authorization, request authority, budget, cancellation, started/terminal pairing and reconciliation path as other capabilities. Changing text requires separate exact permission.

Trusted `content.inspect` takes `{session_id, task_id?, name}` and maps to `content_inspect`; an explicit Task must belong to that Session. It may inspect during recovery without running a model or settling unknown effects. SDK reads return `Busy` instead of blocking on the content transaction lock. Model calls may wait with cancellation; after acquiring the lock, a bounded synchronous transaction completes without a detached background write. Process-exit recovery distinguishes uncommitted staging, committed content without a Core terminal, and an already committed Core result. It never replays the original write. A trusted verifier can bind the original call to the independently read record and bytes; this does not rewrite the original parent-tool observation.

Missing/corrupt objects remain errors instead of stale-cache reads. Record and retained-object quotas, full revision conflicts, unsafe paths, unsafe modes and changed root identity remain explicit errors. SDK content errors are currently encoded as `runtime_error` over IPC; invalid inspection shape or Task ownership uses `invalid_params`. A complete large `ContentView` can exceed the default IPC frame even when SDK reading succeeds. IPC then returns `response_too_large_outcome_unknown`, retains the connection, and does not establish that content changed. There is no content chunking endpoint. Issue #18's new evidence certifies these local scenarios; historical Issue #1 evidence does not.

Automatic result externalization preserves the original Host terminal and original Cells value/hash. Only the value delivered to Luau becomes a handle. Before writing the body or metadata, Runtime commits `runtime_result_storage_prepared` with the exact Device, handle, content hash/length, Task, capability key and complete Attempt lease. It writes each content entry once and appends a separate stored/known-failed/unknown terminal. Known storage failure may return the original value. `CommitOutcomeUnknown`, or a prepared operation without a terminal after process exit, blocks enqueue, resume and confirmed Fork across reopen. Ordinary `recover` repairs execution records without clearing that storage obligation or replaying the tool/content writes.

The host-only Rust SDK exposes `pending_result_storage`, `inspect_result_storage` and `reconcile_result_storage`. Inspection retains the original stopped Task and Cells ownership, requires Device process cleanup to be confirmed, and checks that Core and Cells still record the same original success. It reads the exact prepared body/metadata keys and validates their Device, first revision, hash, length and bytes. The host can inspect an absent write, a body without metadata, or a complete result. Reconciliation requires that exact unchanged inspection, a non-deserializable `HostActor`, independent evidence and a mandatory verification callback. A reason alone cannot release the block. After verification, ContentStore confirms the exact observed revisions or absence and syncs its current authority directory under the transaction lock. Reconciliation appends a separate decision, preserving prepared/unknown history and every original terminal; it never repairs content by rewriting it. Changed ownership/content, a live executor and unconfirmed cleanup reject. After any remaining normal recovery, an explicit new task can proceed. These administration methods are not model tools or IPC endpoints.

## Workbench plan review and artifact actions

`session.plan` returns the same `PlanView` as the Rust SDK: Session, Task, Attempt, monotonic version, previous version, source, steps, update time, Core cursor, and `content_sha256`. Each step has `id`, `text` and `status`. The server computes `content_sha256` as SHA-256 of the serialized steps. Clients retain the returned digest rather than recomputing it with a different JSON serializer.

`plannotator.submit` requires `{session_id, expected_task_id, expected_version, expected_content_sha256, decision, comments?, summary?, actor?}`. The three `expected_` values identify the plan the user actually reviewed. The server checks them against the authoritative current plan and commits the feedback under the same coordination lock used by plan updates. A changed Task, version or digest returns `invalid_params` with a version conflict and records no feedback. The server derives the annotation target, path and digest; clients cannot supply a target. A client must ask the user to review a newly read plan before submitting new feedback. It must not silently attach old notes to that plan. `plannotator.list` takes `{session_id}`. Feedback application on a later Attempt checks the plan identity again.

The sole artifact RPC namespace is `artifacts.*`:

| Method | Parameters and result |
| --- | --- |
| `artifacts.put`, `artifacts.update` | `PutArtifactRequest` / `UpdateArtifactRequest`; returns `ArtifactRecord` |
| `artifacts.preview` | `{artifact_id}`; returns `ArtifactPreview` with HTML, content type and version |
| `artifacts.list` | `{session_id}`; returns Session-owned records |
| `artifacts.action` | `ActionRequest`; returns `ActionOutcome` after Runtime/Host dispatch |
| `artifacts.action_list`, `artifacts.action_get` | `{session_id}` / `{action_id}`; returns action record(s) |
| `artifacts.action_cancel` | `{session_id, action_id}`; checks ownership before cancelling the original action/task |
| `artifacts.recovery_save`, `artifacts.recovery_load` | `{}`; saves or loads the workspace recovery bundle |

The singular `artifact.*` methods and the alternative `artifacts.action_dispatch` / `artifacts.actions_list` names are removed. Runtime audit event kinds such as `artifact.action.applied` remain event names. They are not RPC aliases. Follow-up actions enqueue a real Task; tool actions use the existing exact permissions and Host dispatch. An artifact button does not grant new permission.

`device_id` is optional routing metadata accepted only by the WebUI gateway for `session.create` and `session.fork`. The gateway selects a registered Device endpoint, removes this field before Runtime dispatch, and saves the returned Session ownership. Direct Runtime calls reject it as an unknown field. The current fork API operates on the source Device; requesting another Device returns an error because this API does not migrate Sessions. An unknown Device never falls back to local execution. If Runtime accepted a request but ownership persistence failed, the gateway returns `ownership_persist_outcome_unknown`; inspect the owning Device before retrying.

Editor and Trace Debug open at the exact local addresses printed by their own services. Their pages perform separate token login. Project/page selection and captured Sessions come from service startup configuration. The workbench does not place tokens, page selectors or Session selectors into launch URLs. These current contracts do not expand any historical validation claim below.

## Events and reconnect

Events are durable pull pages, not an ephemeral push channel. `events(session, after, limit)` excludes `after`; accepted limits are 1 through 1000. A future cursor is an error. `wait_events` and IPC `session.events` with `wait_ms` wait for a page, cancellation or the bounded wait deadline (at most 30 seconds). An empty page means no events were available before that deadline; it is not a Session terminal.

A consumer keeps the last contiguous event it has processed. It saves `{session_id, after}` durably before closing its connection. The example validates each cursor, writes a new file, calls `sync_all` on that file and its containing directory, and only then closes the event client's socket. It preserves a separate control connection so a subscription disconnect cannot cancel that connection's active prompt. On a new explicit connection it reads the cursor from disk and requests only the suffix. The example compares the entire resumed suffix with the Core log and also checks that saved prefix plus suffix equals the full log, with one original task and one user prompt.

Disconnecting the connection that owns an active `session.prompt` instead cancels that RPC and its Runtime execution. The original transport error may remain `outcome_unknown:true`; inspect the durable task and Session separately. A saved cursor allows reading what happened; it does not authorize resending the prompt. There is no automatic reconnect or replay.

## Pairing and state transitions

| Condition/action | Required resulting behavior |
| --- | --- |
| Idle Session receives explicit prompt | New Task, Attempt, Worker/fence; Session running |
| Exact Host capability needs permission | Durable planned call and pending approval; Session awaiting approval; no Host effect yet |
| Allow once | Only the exact target/scope can start; another capability needs its own approval |
| Deny | Call is not executed; denial cannot be overwritten or bypassed by another approval for the same task/scope |
| Cancel while pending | Pending request is denied/closed, no file effect; task becomes cancelled and late allow cannot revive it |
| Known call terminal | Stored once for the exact call/arguments/attempt; duplicate, unknown call, changed arguments/name or old-lease result rejected without appending |
| Active RPC connection closes | Original RPC conservatively reports uncertainty; execution cancellation and durable task state are inspected separately |
| Claimed owner exits before an Attempt begins | Explicit recovery detaches the old claim, fences its identity and retains the original queued Task/input/fairness position; only explicit resume can dispatch it |
| Started effect has no durable terminal | Explicit recovery retains original `outcome_unknown`; Session needs reconciliation and refuses new work/fork |
| Trusted host verifies original effect receipt | Explicit reconciliation appends evidence for that original call; no source or prompt replay |
| Explicit next task after a known recovery | Same Session, new Task/Attempt/Worker and higher fence |

Cancellation requires the original Task identity. Retain the admitted Task ID, read that exact `TaskRecord`, and construct `TaskRecord::cancel_target()`. `CancelTarget` contains `session_id`, `task_id`, `worker_id: Option<String>`, `attempt_id: Option<String>`, and `fence: u64`. This fence belongs to the Task queue, not the Core Session lease. IPC `session.cancel` takes this serialized object directly; the old `{session_id}` parameters are rejected. A newly accepted, unclaimed queued Task has no Worker/Attempt and fence 0. Recovery can retain a higher fence, and queued readmission after approval retains the original Worker/Attempt. A caller must read the exact original Task again before cancelling after any such transition. A mismatched identity returns `StaleCancellation` (`stale_cancellation` over IPC). The same identity after its Task becomes terminal returns false, even when the same Session has a second queued or active Task. A consumer never replaces the original Task with the Session's current task.

Cancellation and task completion are ordered by the durable queue write transaction, including cancellation from a separately opened Runtime or its authenticated IPC handler. If cancellation commits first, a known task ends as `cancelled` with exactly one `run_cancelled` audit record. If completion commits first, later cancellation returns false and cannot rewrite the terminal. When task request authority is configured, it stays Closing through original work/process cleanup and ends from that same terminal decision under lifecycle coordination. Genuine unknown effects retain `outcome_unknown` (Requests records failed); failed cleanup keeps the original task draining and its capacity reserved for explicit recovery. Cancellation never clears either condition. If Requests ended but the queue terminal commit failed, cancellation returns a recovery-required error instead of acknowledging a conflicting terminal; capacity stays held until explicit recovery. Pending approval cannot authorize the cancelled task or an explicit replacement, which requires fresh permission and a new worker/attempt/fence.

Session `idle` is reusable; it is not a permanent terminal for the whole conversation. Task, call, execution and approval terminals are immutable. A new task cannot alter an old terminal. An explicit cancellation of the original `CancelTarget` retains `cancel_requested` on that task. Transport-token cancellation can instead retain a cancelled terminal with `cancel_requested:false`; inspect both facts instead of inferring which cancellation path ran from that flag alone. `Runtime::cancel` repeated after task completion reports false. Ordinary result errors must mean known failure; an uncertain side effect must be recorded as unknown. Neither reopen, cancel, finish, repeated recovery nor fork converts uncertainty to known success.

Background commands retain their own original executor, process identities and Device cleanup records. Parent Task cleanup is not evidence that a background command stopped. The trusted Rust SDK exposes `background_confirm_cleanup(id, evidence, verify_stopped)`. Its callback receives the public `BackgroundCleanupInspection` with the original task, optional supervisor, known processes and an incomplete-identity flag. Missing identities require independent host records. The confirmation is bound to the exact task ownership and identity snapshot and survives reopen; it records cleanup only. The host then explicitly calls `background_recover` with a known result and separate evidence. RPC recovery cannot create this host confirmation from a reason string. Known terminals remain immutable.

The standalone package's tests call the public Core API to reject mismatched, duplicate and cross-attempt tool results and check that neither cursor nor projection changes after rejection. Existing Core/IPC/Runtime tests cover the underlying state transitions and transport pairing. None of the new client proofs edits append-only SQL records.

## IPC version, errors and limits

IPC frame version is **1**. Core event/store version is **3**. These are different layers. `runtime.health.protocol_version` reports the Core version; it must not be used as the outer IPC frame version. A connection starts with authenticated `hello`. An incompatible outer version receives `unsupported_version` with the request ID and the server closes the connection before business dispatch. There is no fallback downgrade. The full strict frame contract and bounded defaults are in [`cayw-ipc/README.md`](../crates/cayw-ipc/README.md).

Every wire frame is one bounded JSON object followed by LF. Response IDs must correspond to a fully written, currently pending request on that same connection. Unknown, early, duplicate, malformed or wrong-version responses close the connection and conservatively fail remaining requests. Authentication and all resource limits come from the host; the example token is public synthetic data. Only loopback addresses are accepted. This transport is not a remote TLS service or operating system security boundary.

`ClientError` contains `code`, `message`, and `outcome_unknown`. For example:

| Error | Meaning and caller action |
| --- | --- |
| `unsupported_version`, `unauthorized` | Handshake rejected; fix contract/token before explicit new connection |
| `invalid_params`, `request_too_large`, `client_busy` | Local validation/capacity rejection before dispatch; outcome known |
| `stored_data_corrupt` | Persisted JSON is invalid; this is not an invalid client parameter and must not be retried as a new request |
| `busy` | Server's in-flight handler limit rejected dispatch; outcome known |
| `stale_approval`, `session_error` | Runtime rejected the request; inspect message/current Session |
| `needs_reconciliation_outcome_unknown` | Original unknown effect blocks new work; `ClientError.outcome_unknown` is true; submit actual host evidence |
| `storage_busy`, `storage_full`, `storage_io`, `storage_corrupt`, `storage_error` | Typed persistence failure; distinguish contention, disk capacity, I/O and corruption without matching message text. Inspect the original operation before retrying |
| `storage_busy_outcome_unknown`, `storage_full_outcome_unknown`, `storage_io_outcome_unknown`, `storage_corrupt_outcome_unknown`, `storage_error_outcome_unknown`, `stored_data_corrupt_outcome_unknown`, `request_clock_invalid_outcome_unknown` | Requests authority failures retain their existing unknown state while exposing the concrete cause. A storage category does not prove rollback or permit replay |
| `content_commit_outcome_unknown`, `content_error`, `workspace_error` | Content commits that may have completed retain unknown state; other content/workspace failures preserve their own category |
| `worker_failed`, `worker_panicked_outcome_unknown`, `worker_lost_outcome_unknown`, `agent_error`, `agent_outcome_unknown` | Typed worker/agent distinction. A panic or lost worker keeps `outcome_unknown` true; it is not an ordinary known failure or an automatic retry |
| `cancelled_outcome_unknown`, `timeout_outcome_unknown` | RPC cancelled/timed out after admission; inspect durable records |
| `connection_closed`, `connection_lost`, `protocol_error` for in-flight calls | Original request may have run; inspect durable state, never blindly retry |

Runtime error messages include the RPC method and only the supplied session/task IDs as bounded operation context. Prompt text and arbitrary parameters are not copied into the message. Error codes and `outcome_unknown` are derived from typed causes, including nested `recovery_required` causes and cleanup errors, so a false wrapper flag cannot make a nested unknown effect look known. The independent headless client preserves these codes and states in both SDK and IPC modes.

A queue JSON decode failure wrapped in SQLite's `FromSqlConversionFailure` is classified as `storage_corrupt` by its typed JSON cause. Other conversion failures retain their own classification; the original source is preserved. A caught Runtime worker panic preserves a string payload with control and non-printing characters escaped for display. Non-string payloads use `non-string panic payload`. Either form keeps `worker_panicked_outcome_unknown`, explicit recovery and the original admission hold.

The client and server intersect declared frame/in-flight/ID limits. Local over-capacity calls fail before sending; server over-capacity calls return `busy`. A bounded response queue closes a slow connection if it fills. Reads and writes have deadlines. A too-large or unretainable handler response can be unknown after effects; a locally rejected oversized request is known unexecuted. Cancellation targets a request in the same connection using a distinct request ID; original and cancellation acknowledgments are separately paired. Dropping an admitted client request future closes the shared connection. Explicit `request_with_cancel` keeps polling that request to its terminal. Transport cancellation alone does not prove side effects were undone.

## Reproduction and limits

Use the exact commands in the downstream README. The client's `all` command runs six independent scenarios and writes a machine-readable acceptance result plus raw events, views, task identities, saved cursors, child readiness/exit facts and synced synthetic receipts. Every output file is created exclusively; use a fresh output directory on each run.

The local evidence bundle records baseline/final source hashes, nested dependency identities, exact commands, environment, exit codes, logs, executable hashes and requirement rows. The cancellation repair retains an exact 403-file baseline separately, changes only the relevant Runtime/test/client/contract files and records the replayable patch. The root Cargo manifests/lock remain unchanged. The downstream lock keeps its actual smaller graph and the same frozen third-party identities as the root lock. No dependency upgrade is part of this delivery.
